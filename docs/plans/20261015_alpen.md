# Product Specification: ALPEN Productivity App

## 1. Objective

Build a productivity application inspired by OmniFocus, organized around the ALPEN daily planning method:

- **A — Aufgaben notieren:** Capture tasks.
- **L — Länge schätzen:** Estimate task durations.
- **P — Pufferzeiten einplanen:** Reserve buffer time for interruptions and unexpected work.
- **E — Entscheidungen treffen:** Prioritize, schedule, defer, delegate, or drop tasks.
- **N — Nachkontrolle:** Review the day and improve future planning.

The core principle is to help users create a realistic daily plan that fits within their available time, rather than merely maintaining a list of tasks.

## 2. Task Data Model

Implement a Task entity with the following properties:

- `id`: Unique identifier.
- `title`: Required, actionable task description.
- `notes`: Optional description, instructions, and links.
- `status`: `inbox`, `ready`, `scheduled`, `in_progress`, `completed`, or `canceled`.
- `priority`: `A`, `B`, `C`, or `someday`.
- `estimated_minutes`: Expected duration, required before scheduling into a capacity-managed plan.
- `actual_minutes`: Actual effort, recorded manually or through a timer.
- `due_at`: Optional hard or soft deadline; support a deadline type if needed.
- `available_at`: Optional earliest date and time at which the task can be started.
- `scheduled_date`: Optional date allocated for working on the task.
- `scheduled_start`: Optional planned start time.
- `project_id`: Optional parent project.
- `tags`: Zero or more contexts, such as `computer`, `phone`, `errands`, or `deep_work`.
- `recurrence_rule`: Optional repeat rule.
- `plan_order`: Position in the daily execution sequence.
- `completed_at`: Optional completion timestamp.
- `created_at` and `updated_at`: Timestamps.
- `carry_over_policy`: Behavior when incomplete, such as `reschedule`, `return_to_inbox`, or `manual_review`.

Tasks should retain their identity when moved between days. Rescheduling must not create duplicate tasks.

## 3. Priority System

Implement four manually assigned priority levels:

- **A — Critical:** Must be addressed today because of serious consequences, a hard deadline, or a critical commitment.
- **B — Important:** Meaningfully advances important goals, projects, or responsibilities.
- **C — Optional:** Useful but low-consequence; do when capacity remains.
- **Someday — Not committed:** Keep for future consideration, or discard.

Priority indicates importance, not execution order or deadline.

Keep these concepts separate:

- `priority`: Importance of the task.
- `due_at`: Deadline.
- `scheduled_date`: Intended workday.
- `plan_order`: Position in the daily sequence.
- `estimated_minutes`: Expected effort.

Allow users to manually override the suggested order. Never assume all A tasks can fit into a single day; surface overload explicitly.

## 4. Daily Plan Data Model

Create a separate DailyPlan entity for each planning date.

Properties:

- `id`
- `date`
- `available_minutes`: Total working capacity after fixed commitments.
- `buffer_percentage`: Configurable buffer allowance, defaulting to 40%.
- `buffer_minutes`: Derived buffer allocation.
- `planned_task_ids`: Tasks allocated to the day, in execution order.
- `planned_minutes`: Sum of estimated durations for planned tasks.
- `actual_minutes`: Actual effort recorded during the day.
- `unplanned_minutes`: Time consumed by interruptions or unexpected work.
- `review_notes`: End-of-day reflection.
- `created_at` and `updated_at`.

Treat buffer as protected capacity, not as an ordinary task. Allow users to configure the buffer percentage.

Calculate:

- `buffer_minutes = available_minutes × buffer_percentage`
- `usable_minutes = available_minutes − buffer_minutes`
- `planned_minutes = sum(estimated_minutes for active tasks in the plan)`
- `remaining_minutes = usable_minutes − planned_minutes`

Flag the plan as overloaded when `planned_minutes > usable_minutes`. Account for fixed calendar commitments when determining `available_minutes`, if calendar integration is supported.

## 5. Core Workflow

### Capture

Provide a fast inbox for adding tasks without requiring users to fill out every field.

### Clarify

Allow users to assign a project, priority, duration estimate, deadline, availability date, and tags.

### Plan the day

Provide a daily planning interface that:

1. Shows the day's available capacity and protected buffer.
2. Lists eligible tasks that can be scheduled.
3. Suggests a planning order based on priority, deadlines, dependencies, and availability.
4. Allows drag-and-drop or equivalent manual ordering.
5. Displays planned duration, usable capacity, and remaining capacity.
6. Warns when the plan exceeds available capacity.
7. Makes it easy to defer, delegate, or drop tasks.

### Execute

Provide a focused view of today's ordered tasks, with completion controls and optional time tracking. Show estimated versus actual duration where available.

### Review

At the end of the day:

1. Show completed and incomplete tasks.
2. Compare estimated and actual effort.
3. Record interruptions and unplanned work.
4. Prompt the user to keep, defer, delegate, or drop incomplete tasks.
5. Carry selected tasks forward without duplicating them.
6. Use historical estimates to inform future duration estimates, but never silently change user-entered estimates.

## 6. Views

Implement these primary views:

- **Today:** Ordered daily plan, capacity meter, and buffer.
- **Inbox:** Captured tasks awaiting clarification.
- **Upcoming:** Tasks scheduled for future days.
- **Projects:** Tasks grouped by desired outcome.
- **Forecast:** Upcoming deadlines and workload by day.
- **Someday:** Tasks without a current commitment.
- **Review:** Daily completion and estimation feedback.

Support filtering by priority, project, tag, status, and deadline.

## 7. Scheduling and Priority Rules

The scheduling engine should:

- Exclude completed and canceled tasks.
- Respect `available_at`, deadlines, and task dependencies when applicable.
- Suggest A tasks before B tasks, and B before C, while considering deadline urgency and feasibility.
- Never interpret a due date as an automatic scheduled date.
- Never schedule work before its availability date.
- Avoid placing work beyond usable daily capacity without showing a clear overload warning.
- Distinguish hard deadlines from target dates.
- Allow manual overrides and preserve user-selected execution order.
- Never automatically discard tasks.
- Treat Someday tasks as unscheduled unless explicitly promoted.
- Treat estimated durations as planning estimates, not guaranteed completion times.

The initial version can use deterministic rules rather than a complex scoring algorithm. Explain scheduling suggestions and let the user override them.

## 8. User Interface Principles

- Optimize for fast capture and low-friction daily planning.
- Make duration and capacity visible throughout the planning workflow.
- Use a clear visual distinction between priority, deadline, and scheduled date.
- Make overload warnings informative, not punitive.
- Keep advanced metadata out of the way until needed.
- Support keyboard-first interaction where practical.
- Make rescheduling and carry-over explicit.
- Use responsive layouts suitable for desktop and mobile.

## 9. MVP Scope

Build in this order:

1. Task CRUD, inbox, and persistence.
2. Projects, tags, and priority levels.
3. Daily plans with duration estimates and buffer calculations.
4. Today view with manual ordering and overload warnings.
5. Rescheduling and carry-over.
6. End-of-day review and actual-duration recording.
7. Upcoming and project views.
8. Recurring tasks and optional time tracking.

Defer calendar integrations, AI-generated estimates, advanced dependency graphs, and automated optimization until the core workflow works reliably.
